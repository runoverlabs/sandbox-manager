# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex, and anything else that reads `AGENTS.md`) when working with code in this repository. `CLAUDE.md` only imports it; edit this file.

## What this is

`msb-manager` manages [microsandbox](https://github.com/microsandbox/microsandbox) microVMs as per-project agent sandboxes: deny-by-default egress, credentials substituted host-side (never inside the VM), one CLI/picker to start, stop, rebuild and update them. Developed against `msb` 0.7.6, host now on 0.7.7 (behaviour re-checked on both, except that **0.7.7 guests have no nested KVM** — `spikes/11-nested-kvm-by-version.sh` — so the dev sandbox can no longer run `msb` while the host is on 0.7.7); `msb --help` is more reliable than its published docs.

`msbctl` runs on the **host** and needs `/dev/kvm` plus the `msb` binary. As observed on 2026-10-05 (host on `msb` 0.7.6) the dev sandbox had nested KVM and could reach GitHub, so `msb` 0.7.6 can be installed here from its GitHub release (`install.sh` from the release assets, checksum-verified) and `msbctl` run for real against throwaway sandboxes. Docker Hub is *not* reachable (`index.docker.io:443` is refused), so load an image instead: `podman save --format oci-archive` then `msb load -i`, and create with `--pull never`. Use a throwaway `MSB_CONFIG_DIR`/`MSB_STATE_DIR`, and always `msb rm -f` what you create. Otherwise syntax-check with `python3 -m py_compile msbctl` and `bash -n`.

## Hard constraints

- **No dependencies.** Python 3.11+ stdlib (`tomllib`) and the `msb` binary only. No pip, no TOML writer. Registry entries are rendered whole from `templates/` and only read back via `tomllib`; the single exception is the `[versions]` table that `update` rewrites (`write_version_override()`).
- `.gitignore` blocks `*.env` and `secrets/`. Nothing machine-local or generated belongs in the repo.
- Comments in config/templates are the documentation (failure modes are non-obvious and cost debugging sessions). Preserve and extend them when changing behaviour; `msbctl --help` and `defaults.toml` are the user-facing docs.

## Changelog, CI and releases

- **Every behaviour change gets a ONE-LINE entry in `CHANGELOG.md`**, under `## [Unreleased]` in the matching `### Added` / `### Changed` / `### Fixed` / `### Removed` group. One line, user-facing, what changed and what a user must do about it (e.g. "needs a rebuild"). No file lists, no rationale, no commit hashes; the commit message and code comments carry those. Refactors, test-only and CI-only changes with no user-visible effect need no entry.
- `scripts/check.sh` is the static check suite and is exactly what CI runs (syntax, shellcheck, ruff with the rules in `ruff.toml`, the unit tests, TOML, `PAYLOAD` in step between `install.sh` and `package.sh`, tracked modes, gitleaks). Run it before committing. `scripts/smoke-install.sh` packages and installs into a throwaway HOME.
- Tracked modes: a file with a shebang is 755, everything else 644, except `bootstrap.sh` (piped into the guest, never executed from disk, so 644). `sed -i` and some editors recreate a file without its executable bit; `check.sh` reads the git index, so `git add` after any `chmod`.
- Releases are tag-driven (`.github/workflows/release.yml`): move the Unreleased entries under `## [X.Y.Z] - YYYY-MM-DD`, set `VERSION`, merge, then `git tag vX.Y.Z && git push origin vX.Y.Z`. The workflow refuses if the tag, `VERSION` and a non-empty changelog section disagree. Never publish by hand with `gh release create` unless the workflow is broken.
- Workflows use `pull_request`, never `pull_request_target`, with read-only default permissions; actions are pinned by commit hash with the version in a comment (Dependabot keeps them current).

## Layout

- `msbctl` — single-file Python CLI (~1900 lines). `Sandbox` class (config resolution, `msb` flag emission), `cmd_*` handlers, `main()` argparse at the bottom, fzf menu with numbered-prompt fallback.
- `msb-picker` — fzf picker used by the desktop entry (`msb-manager.desktop`).
- `bootstrap.sh` — runs once **inside the guest** at create time. `msbctl` pipes it in over stdin (not mounted, so manager code stays out of the VM). Intentionally not `set -e`: every step records its outcome and failures are summarized together so an allowlist can be built in one pass. Parameterized by `MSB_*` env vars.
- `install.sh` — two modes: `--dev` (a git checkout; symlinks the commands into it) and `--package` (copies the tree to `~/.local/share/msb-manager/versions/<v>/`, `current` link, commands link through it; keeps current + previous). Seeds `~/.config/msb/` from templates, never overwrites, `--uninstall` removes only what it owns. Never reads stdin (it runs under `curl | sh`) and has no backticks in its unquoted heredoc (they execute).
- `get.sh` — the `curl | sh` entry point (POSIX sh, modeled on microsandbox's installer): resolves the latest release via the GitHub API, downloads the tarball, verifies its sha256, runs the installer inside it. `@@GITHUB_REPO@@` is filled in by `scripts/package.sh`; `MSB_MANAGER_BASE_URL` (+ `--version`) serves assets from a mirror or `file://` for testing.
- `scripts/package.sh` — builds `dist/` (reproducible tarball, repo-bound `get.sh`, `checksums.sha256`) from an explicit PAYLOAD list (keep in step with `install.sh`); fails on symlinks, `.env` files or an unreplaced placeholder; normalizes modes. Does not publish.
- `VERSION` — the release version; `msbctl --version`, `msbctl self-update` (re-runs the packaged `get.sh`; a checkout says `git pull`).
- `profile/CLAUDE.md` — the SHIPPED central CLAUDE.md. `assemble_profile()` appends the operator's `~/.config/msb/CLAUDE.local.md` and writes the result to `~/.local/state/msb/profile/` (a real file, shared by every sandbox); that directory is what is mounted read-only and copied into each sandbox's `~/.claude` on every start. Nothing mounts or links a path inside the checkout or install tree. `ensure_profile()` then appends `sandbox_profile_section()` (the sandbox's `current_features()`, one line each) to the guest's copy only, passed as an argument, never spliced into the script. Editing the copy in a sandbox does nothing.
- `defaults.toml` — what msb-manager ships: egress rule groups, version pins, baseline defaults. Read from the checkout, never copied.
- `templates/` — `config.toml.in` (the short skeleton of *local* overrides install.sh writes once), `sandbox.toml.in`, `dev.yaml.in`, `registry.toml.in`, `registry-repo.toml.in` (a sandbox with no folder).
- `.msb/` — this repo's own sandbox policy (`sandbox.toml`, `dev.yaml`).
- `docs/` — the documentation site (GitHub Pages, `.github/workflows/docs.yml`). Pages are Markdown in `docs/content/` with `title`/`section`/`order` front matter; `docs/build.py` is a stdlib-only converter for a deliberate Markdown subset (extend it rather than adding a generator), plus `template.html` and `assets/` (terminal theme, light/dark/auto, client-side search over an index it writes as a script so the site works off `file://`). `CHANGELOG.md` is rendered as a page, never copied; the logo comes from the repo-level `assets/`. The same build writes the SEO/agent outputs (canonical, Open Graph, JSON-LD, `sitemap.xml`, `llms.txt`, `llms-full.txt`, a `.md` copy of each page), all derived from the pages and `--site-url`, so a new page needs only its front matter — including the `description`, which `--check` requires. `--check` (run by `check.sh`) fails on a broken internal link or anchor and on any `msbctl` subcommand without a `### \`msbctl <name>\`` section on the Commands page. **A user-visible change updates the relevant page in the same PR**, like its changelog line.
- `assets/` — the logo: `msb-manager-mark-dotmatrix-dark.svg` (for dark grounds, also readable on light; the README's header) and `msb-manager-icon.svg`.
- `scripts/screenshots/` — `make.sh` regenerates `docs/assets/screenshots/*.svg` (used by the README): the real `msbctl`/`msb-picker` in a fixed-size tmux against an invented HOME (`world.py`), a fake `bin/msb` and a `bin/msbctl` wrapper that skips only the `/dev/kvm` preflight; `render.py` turns the captured grid into an SVG terminal (fixed cells, box lines drawn as strokes, docs palette). Needs tmux and fzf. Re-run it when a screen it shows changes; never hand-edit the SVGs or put real names, hosts or tokens in `world.py`.
- `tests/` — stdlib `unittest`, run by `check.sh`: `tests/harness.py` (`MsbctlTest`) gives each test a throwaway HOME and a freshly loaded `msbctl`, with `preflight()` and the agent filter patched out and the network off; `tests/fake/msb` records argv and the env vars a test names, keeps state, and exits 2 on any call it does not know. Assert what reaches `msb`, and with `assert_not_in_argv()` that a planted secret does not.
- `spikes/NN-*.sh` — re-runnable PASS/FAIL scripts, one per mechanism the design relies on (SSH agent over vsock, mount ownership, per-port rules, persistence, hostname rules, memory reclaim, token placeholders, profile seeding, DNS rebind). Run one with `./spikes/07-claude-token-secret.sh`. Several need host-specific env vars (e.g. `ALLOW_HOST`, `ALLOW_PORT`) with no defaults, on purpose. Each must assert both the allowed and the denied half.

## The current folder names a sandbox

`sandbox_here()` resolves an omitted name (or `.`) to the registered sandbox whose `project` contains the cwd, deepest wins; the registry decides, never a `.msb/` alone, and two entries on one folder are an error. `main()` applies `resolve_here()` to `args.name`/`args.names` for every verb but `_agent-filter`, and rewrites `exec --` to `exec . --`. A name is optional (`nargs="?"`/`"*"`) ONLY where it is the sole positional; where another positional follows it stays required and `.` is the shorthand, so nothing is ever ambiguous (`observe on` must not mean the sandbox "on"). `guest_workdir()` maps the cwd to the same subfolder of the guest project path for `shell`/`exec`.

## Sandboxes without a folder

`source = "repo"` entries (`msbctl add --repo`, `cmd_add_repo()`) have `repo`/`ref` and no `project`. `Sandbox.project` is then `policy_dir(name)` (`STATE_DIR/policy/<name>/`): the repo's `.msb/sandbox.toml` and `dev.yaml` fetched by `fetch_repo_policy()` through `github_api()` (which, unlike `http_json()`, tells a 404 — "no file" — from every other failure, and dies on the latter) at a resolved commit, plus `meta.json`. It is never mounted; the clone is a named disk volume (`workspace_volume`, `-workspace`) at `guest_project`, made by bootstrap's `do_clone` (`MSB_CLONE_URL`/`MSB_CLONE_REF`) with an inline credential helper handing git the `GH_TOKEN` placeholder. `rebuild` never refetches (`ensure_repo_policy()` only fills a missing dir, at the approved `_commit`); `msbctl policy <name> update` moves the pin. `project_policy()` includes `_commit`. For these sandboxes `extra_rules` and `secret_binds` from the registry ADD to the repo's (`registry_binds` tracks which may use `global.env`), `edit_target()` is always the registry, `require_project_file()`/`code`/`move` refuse, `guest_path` may be neither `"host"` nor dotted, GH_TOKEN is always bound when stored, and `ssh_keys = []` lets the agent filter run with no host agent at all.

## Where the project is mounted

`Sandbox.guest_project` is the registry entry's `guest_path` (`"host"` = the host path, `"/work"`, or an absolute path; default from `[defaults]`, else `/work`), validated by `guest_path_problem()`. Registry-only — a host path must never reach the committed `sandbox.toml`. Everything that names the guest project goes through it: the mount, `--workdir` at create (overrides the committed `dev.yaml`), `guest_workdir()`, Claude's folder trust in `ensure_profile()`, bootstrap's `MSB_PROJECT_DIR`, and the extra-mount overlap check (`parse_mount_spec(spec, project_dest)`). Never hard-code `/work`; use `GUEST_PROJECT` only as the default.

## Configuration model

Four TOML files, later wins:

1. `<repo>/defaults.toml` — shipped: egress rule groups, pins, baselines (updates with `git pull`)
2. `~/.config/msb/config.toml` — the operator's overrides only, merged over (1): tables merge key by key, anything else (incl. a rule group) is replaced whole. `msbctl config` shows the result and each value's origin
3. `<project>/.msb/sandbox.toml` — committed, portable, no host paths or tokens
4. `~/.config/msb/sandboxes/<name>.toml` — machine-local paths and overrides

Put new defaults and rule groups in `defaults.toml`, never in the template skeleton.

A project's `dev.yaml` is **never passed to msb**: msbctl reads its `image:` line (validated as an OCI reference by `image_problem()`, because msb boots a host directory given as the image — spike 12) and nothing else, and create/rebuild refuse a file with any other top-level key than `CONF_KEYS_READ` or any nested line (`conf_problems()`). msb's `--conf` is code, not data: it mounts host paths, copies host files in and interpolates `${VAR}` from msb's own environment, which holds the bound secrets, and the project folder is writable from the guest. Everything is emitted as flags instead (egress as verified `--net-rule` flags from the `sandbox.toml` group list). `conf` must stay inside the project. The operator's escape hatch is `msb_conf` in the registry entry (registry-only, absolute path, no `${`). Env overrides: `MSB_CONFIG_DIR`, `MSB_STATE_DIR`.

## Wizard features

`msbctl add` asks for *features*, not raw egress groups. `FEATURES` in `msbctl` maps each one to the egress groups, apt packages and bootstrap switches it needs (e.g. `bun` → `bun` group + `bun = true`; `gitleaks` is opt-in, never preselected; `podman` → `containers` group + packages + a storage follow-up). A feature's `languages` are GitHub linguist names; `detect_features()` reads the repo's languages from the GitHub API and preselects features at ≥5% of bytes. Add a new feature there rather than teaching users to tick a group and a package separately. Coding agents are a separate `AGENTS` list (only `claude` for now, preselected); an agent is installed only if ticked, so add new ones there plus an installer step in `bootstrap.sh`. Groups neither list owns still get their own toggle. Package caches (`pick_caches()`) are named disk volumes, kept across rebuilds and deleted by `purge`. After features, `pick_disks()` asks for the root disk size (small/medium/large/custom around the usual 16G) and, if podman is in, a container disk — or none, which means `fuse-overlayfs` on the rootfs. Single-choice prompts use `choose_one()`; all multi-choice prompts go through `toggle_list()`: a stdlib `termios` menu (arrows/jk, space, enter) on a terminal, numbered input otherwise — keep both paths working, since tests pipe stdin.

## Editing an existing sandbox

`msbctl edit <name>` (the picker's `e`) is the wizard as a menu of sections, one at a time: `EDIT_SECTIONS` in `msbctl` (name & folder, features & agents, resources, package caches, container storage, extra folders, egress rules, published ports, SSH keys, Claude token, GitHub token, secrets, identity & autostart) plus "view the CLAUDE.md it gets" (`sandbox_claude_md()`, read-only) and "edit the files in your editor". Each `section_*` reuses the wizard's own `pick_*` function preselected from the sandbox's current state, writes back with `set_toml_key()` (an in-place, comment-preserving, parse-checked single-key editor — never rewrite a whole file), and either applies live (resources via `msb modify`, keys, secrets) or adds to `ctx["rebuild"]`, which `Done` turns into a rebuild offer. Portable settings go to the project's `.msb/sandbox.toml`, machine-local ones (mounts, published ports, identity, Claude token, ssh keys, autostart) to the registry entry; `edit_target()` writes to the registry only if it already overrides that key. Esc inside a section returns to the menu. If a hand edit leaves a file unparseable, `_recover_broken()` offers the editor instead of locking you out. A new wizard step should get a matching section. msb can rename neither a sandbox nor a volume, so `rename_sandbox()` (`msbctl rename`, the name & folder section) removes the VM, moves everything msbctl keys by name (entry, `secrets/<name>.env`, Claude state, agent log, versions cache) and recreates it; existing disk volumes keep their old prefix through the entry's `volumes` key, and `name_problem()` refuses a new name that is still another sandbox's prefix. `move_project()` (`msbctl move`) repoints `project`, copies `.msb/` over if the new folder lacks it, re-derives `repo`, and needs a rebuild. Per-sandbox secrets (`secrets/<name>.env`) are written ONLY through `set_env_file_value()`/`store_secret_value()` — never by truncating the file, which once erased every other secret in it.

## Scripting interfaces

`ls --json` (`ls_data()`) and `show --json` (`show_data()`) print exactly one JSON document on stdout; everything else that runs meanwhile is redirected to stderr. They say whether a secret is *stored*, never its value. `secret set <name> VAR [--stdin] [--restart]` stores a value only for a variable the sandbox already binds (`GH_TOKEN` or a non-reserved `secret_binds` var) — binding a new one is `secret add`, a policy change — and `bind_secret_live()` asks msb (`msb_bound_secrets()`, from `msb inspect`) whether a binding exists before adding one with `msb modify --secret` (`--next-start` / `--restart` on a running sandbox). `setup --claude-token NAME [--stdin]` stores a Claude token with no menu. Values from stdin go through `read_secret_input()` (one trailing newline dropped; empty, whitespace or >8 KiB refused, never echoed).

## A remote host

A remote host is an ordinary install driven over ssh. The laptop's everyday key gets `restrict,pty,command="<msbctl> host serve"` (written by `msbctl host authorize`; `--admin` writes an unrestricted line, meant for an `sk-` key). `host_serve()` shlex-splits `SSH_ORIGINAL_COMMAND`, requires `msbctl` first, and `restricted_problem()` decides with `build_parser()` itself (and `split_cli()`, the same exec/shell flag split `main()` uses): explicit sandbox names only (never `.` or omitted), `msb exec` flags only from `MSB_EXEC_VALUE_FLAGS`/`MSB_EXEC_BARE_FLAGS`, and a verb/argument allowlist commented per refusal. Refused: one stderr line, exit 126. Allowed: `MSB_RESTRICTED=1`, `~/.local/bin` and msbctl's own dir prepended to PATH (sshd's PATH has neither), `os.execv` of the original args. A new verb is refused by `host serve` until it is added there deliberately — and a test row added to `tests/test_host_serve.py`. Anything that approves (`check_policy()`, `policy approve/update`) refuses under `restricted()`; `add --repo` there skips the global token and refuses a policy binding a variable already stored for that name. `host check` (heuristics, `--json`), `host autostart install` (a systemd user unit running `start --autostart`; lingering is root's, once) and `start --autostart` (the picker uses it too) complete the host side. `host` verbs skip the preflight.

## Remotes, on the laptop

`[remotes.<name>] ssh = "user@host"` in `config.toml` (`msbctl remote add|ls|test|rm`). `host:name` is recognised in `main()` AFTER parsing, from `args.name`/`args.names` only — never by scanning argv, since `port web 3000:5173` and `allow web mirror:443` have the same shape. A single-name verb `os.execvp`s `ssh_argv()` + `shlex.join(["msbctl", *original argv with that token made bare])`; a multi-name verb runs one ssh per remote name inside the names loop (`run_remote_verb()`, name right after the verb so `-c a b` cannot swallow it). `-t` only when stdin and stdout are TTYs. `ssh_argv()` shares a ControlMaster per host under `STATE_DIR/ssh/`. `preflight()` skips msb/KVM for remote names, the `remote` verb and `ls` with remotes. `ls` queries remotes in threads (`ls --json`, batch, 15 s), caches answers in `STATE_DIR/remotes/`, serves a failed host's rows as `stale` and does not retry it for `REMOTE_RETRY_AFTER` unless `--refresh`; with no remotes its output is byte-for-byte unchanged. `ls --json` stays local. `status` stays local.

## Machine-level setup and first run

`msbctl setup` is the machine-level twin of `edit`: `SETUP_SECTIONS` (git identities, Claude login, your network, new-sandbox defaults) plus "edit the file", each writing to `~/.config/msb/config.toml` via `set_toml_key()` / `remove_toml_table()` or to `secrets/global.env` via `set_env_file_value()` (0600, keeps the documenting comments). The main menu's "setup" item opens it. `maybe_welcome()` (bare `msbctl` and `add`, interactive only) offers the same sections as a guided walk-through the first time: `needs_welcome()` is true only if there is no `welcome-done` marker AND nothing configured yet, so an already-set-up machine is marked done silently. A group you define under "your network" that names LAN hosts goes in `defaults.private_dns_groups`, which `msbctl add` and `edit` read to set `allow_private_dns`. Claude tokens are named (`claude_tokens()`: `CLAUDE_CODE_OAUTH_TOKEN` is `main`, `CLAUDE_CODE_OAUTH_TOKEN_<NAME>` the rest); `[defaults] claude_token` picks the default and a registry entry's `claude_token` overrides it, and whichever is chosen is handed to msb as `CLAUDE_CODE_OAUTH_TOKEN`, so the guest never knows. A new machine-level setting should get a section here. When testing, `claude` may be on PATH and adds a "run claude setup-token" row to the login menu — patch `shutil.which` so numbering is deterministic.

## SSH agent filtering

Each sandbox's `--vsock` points at its own filtering daemon (`msbctl _agent-filter <name>`, same file, state in `~/.local/state/msb/agent/`), not the host agent. It forwards only identity-list and sign requests, restricted to the fingerprints in the registry entry's `ssh_keys` (absent = all, `[]` = none), re-read per request. The socket path is baked in at create time, so sandboxes created before this need one `rebuild`. Keys are picked in one grouped multiselect (`agent:` / `~/.ssh:` headings via `Header` rows in `toggle_list`); an encrypted key with no `.pub` is listed unnamed and only asks for its passphrase if picked. The fingerprint is the stored/matched identity but is never displayed. `ensure_keys_loaded()` (called from `ensure_agent_filter()`, so every start path) `ssh-add`s any selected key missing from the agent, found by fingerprint in `~/.ssh` (still-unnamed encrypted files are tried in turn), warning rather than failing if it can't. The daemon skips the `msb`/KVM preflight; `ensure_agent_filter()` respawns it on every start.

## What msb can and cannot change (verified on 0.7.6 and re-checked on 0.7.7)

`msb modify` changes cpus, memory, root disk (grow only), env and **secrets** on an existing sandbox, keeping its state — cpus/memory/env need a restart, root disk and secret removal are live. That is what `msbctl resize` and `msbctl secret` use. Network rules, TLS interception, DNS rebind protection, mounts, published ports (`--port`; `modify` has no port option in the 0.7.7 source), owned disks and the image are create-time only (`msbctl allow` / `mount` / `port` record them and need a rebuild). A full snapshot restored with `msb restore --disk-only` can change network rules and mounts *and keep state*, but it drops TLS interception (re-enable via `modify --secret`), env (re-add with `modify -e`) and resets DNS rebind protection with no way back — not built. When applying `modify`, pass `box.secret_env()` (0.7.6 failed if any bound secret's host variable was unset). CLI flags override `--conf`. `msb` does not log egress denials at any level (re-checked on 0.7.7 at `--debug` and `--trace`), but it does log what it ALLOWS: at `--log-level debug` an intercepted connection appears in `~/.microsandbox/sandboxes/<name>/logs/runtime.log` as `TLS intercept sni=<host> dst=<ip:port>`, and a resolved name as a `dns::` line. Nothing is logged for a plain TCP connect on any other port, so off :443 a DNS lookup is the only evidence. That asymmetry is why `egress_mode = "observe"` has to unblock before it can measure. Forking a sandbox with a host mount does not give an isolated workspace (unmapped → EIO; remapped → ESTALE).

**Disks:** `--mount-owned DEST:kind=disk,size=…` is deleted with its sandbox. `--mount-named NAME:DEST:kind=disk,size=…` creates a volume that **outlives** it (so a rebuild keeps it), but the guest path must contain **no dot** ("invalid or reserved device id" otherwise — `/d` and `/mnt/cache/npm` work, `/root/.npm` fails; both versions). That is why caches mount at `/mnt/cache/<key>` and bootstrap symlinks the tool's dotted directory to it. A volume's size is fixed at creation and `create` fails if the requested size differs, so `named_disk_flags()` keeps the existing capacity. `msb volume rm` refuses an attached volume. A directory mount with `quota=` also works but is a virtiofs share, ~12–20x slower for tiny files.

## Egress rule gotchas (easy to get wrong)

- Rules are **first-match-wins**; a leading deny can't be undone by a later allow. The `base` group is always applied first.
- `egress_mode` (`"enforce"` default, `"observe"`) is a per-sandbox, machine-local escape hatch for an allowlist too tight to work in. `observe` emits `--net-default-egress allow`, **no** `--net-rule` at all, `--log-level debug` and `--no-dns-rebind-protection`: nothing is blocked and every host reached is recorded. `msbctl observe <name>` reads that back, flags what no rule covers and prints the `msbctl allow` line; `off` restores deny-by-default. It is written to **and read from** the registry entry only (`self.entry`, never `_pick`) — never `sandbox.toml`, which is committed, writable from the guest, and would ship an unfiltered sandbox to everyone who clones the project; a project's `egress_mode` is ignored with a warning. The rules stay in the config and keep being curated while it is on; they are simply not emitted.
- A hostname rule only inspects HTTPS. On other ports it degrades to the resolved IP set and breaks against address pools. Plain HTTP (:80) is denied outright.
- DNS resolution is part of a rule: an unresolvable name fails identically to an unallowed one.
- Secrets use `msb --secret ENV[:OPTIONS]@HOST`: placeholder in the guest env, real value substituted host-side into request **headers (HTTP Basic auth included)** for the named hosts only. Query strings and bodies are *not* substituted unless the binding opts in with `:query` / `:body`; don't rely on them by default.
- **A placeholder in a request BODY is blocked, and that blocks coding agents.** msb scans every outbound request for its `$MSB_<VAR>` placeholders and kills any request carrying one where substitution is not permitted — the guest just sees its TLS connection drop, which Claude Code reports as `API Error: Connection dropped (ECONNRESET)`. An agent only has to read `$MSB_GH_TOKEN` once (an `env`, a config file) for it to be in its transcript, which is resent on *every* turn: a fresh session works and then degrades permanently. Allowing the host does nothing — this is the secret policy, not the network one. `with_transcript_passthrough()` adds `passthrough=[AGENT_TRANSCRIPT_HOSTS]` to every binding msbctl emits; passthrough lets the harmless *placeholder* travel and never substitutes, so the real value is still headers-only and bound-hosts-only (verified both ways on 0.7.7, including a host that is bound and passthrough at once). `msbctl observe <name>` reports these blocks — they are logged at WARN, so they show up in enforce mode too.
- **Project-layer authority.** `secret_binds` may never name a reserved variable (`is_reserved_var()`: `GH_TOKEN`, every Claude token var) in any layer: create dies, `secret_env()` skips with a warning. A binding from the project's `sandbox.toml` (`bindings_layer == "project"`) takes its value from `secrets/<name>.env` only; the `global.env` fallback is for registry-entry bindings.
- **The policy pin.** `PINNED_KEYS` of the project layer (egress, bindings, `[secrets]`, resources, caches) are applied only once approved: `policy_pin` (digest) in the registry entry, the values in `STATE_DIR/policy-approved/<name>.json`. `refuse_before_create()` (conf problems, reserved bindings, `check_policy()`) runs before a rebuild or rename removes anything. `check_policy()` shows the diff and asks; with no TTY or under `MSB_RESTRICTED=1` (`restricted()`) it dies. Anything that writes a pinned key calls `check_policy()` BEFORE writing (so a pending foreign change is asked about alone) and `approve_policy()` on a reloaded `Sandbox` after: `allow`, `secret add/rm`, the edit sections in `POLICY_SECTIONS` (`approving_edits`). `.msb/` is also mounted read-only over the project (spike 15) — a tripwire only, root in the guest can umount it.
- Some settings are fixed at create time and others changeable on restart — see the comments in `defaults.toml` before moving a setting between them.
