# Edit

Detail carved out of `AGENTS.md`, which keeps only what has to hold in
every session. Repo-specific throughout; the facts here are verified against
msb 0.7.6 and re-checked on 0.7.7.

## Editing an existing sandbox

`msbctl edit <name>` (the picker's Enter, or `e`) is the wizard as a menu of sections, one at a time: `EDIT_SECTIONS` in `msbctl` (name & folder, features & agents, resources, package caches, container storage, extra folders, egress rules, published ports, SSH keys, git push, Claude token, GitHub token, secrets, identity & autostart) plus "view the CLAUDE.md it gets" (`sandbox_claude_md()`, read-only) and "edit the files in your editor". Each `section_*` reuses the wizard's own `pick_*` function preselected from the sandbox's current state, writes back with `set_toml_key()` (an in-place, comment-preserving, parse-checked single-key editor — never rewrite a whole file), and either applies live (resources via `msb modify`, keys, secrets) or adds to `ctx["rebuild"]`, which `Done` turns into a rebuild offer. Portable settings go to the project's `.msb/sandbox.toml`, machine-local ones (mounts, published ports, identity, Claude token, ssh keys, autostart) to the registry entry; `edit_target()` writes to the registry only if it already overrides that key. Esc inside a section returns to the menu. If a hand edit leaves a file unparseable, `_recover_broken()` offers the editor instead of locking you out. A new wizard step should get a matching section. msb can rename neither a sandbox nor a volume, so `rename_sandbox()` (`msbctl rename`, the name & folder section) removes the VM, moves everything msbctl keys by name (entry, `secrets/<name>.env`, Claude state, agent log, versions cache) and recreates it; existing disk volumes keep their old prefix through the entry's `volumes` key, and `name_problem()` refuses a new name that is still another sandbox's prefix. `move_project()` (`msbctl move`) repoints `project`, copies `.msb/` over if the new folder lacks it, re-derives `repo`, and needs a rebuild. Per-sandbox secrets (`secrets/<name>.env`) are written ONLY through `set_env_file_value()`/`store_secret_value()` — never by truncating the file, which once erased every other secret in it.

## Scripting interfaces

`ls --json` (`ls_data()`) and `show --json` (`show_data()`) print exactly one JSON document on stdout; everything else that runs meanwhile is redirected to stderr. They say whether a secret is *stored*, never its value. `secret set <name> VAR [--stdin] [--restart]` stores a value only for a variable the sandbox already binds (`GH_TOKEN` or a non-reserved `secret_binds` var) — binding a new one is `secret add`, a policy change — and `bind_secret_live()` asks msb (`msb_bound_secrets()`, from `msb inspect`) whether a binding exists before adding one with `msb modify --secret` (`--next-start` / `--restart` on a running sandbox). `setup --claude-token NAME [--stdin]` stores a Claude token with no menu. Values from stdin go through `read_secret_input()` (one trailing newline dropped; empty, whitespace or >8 KiB refused, never echoed).
