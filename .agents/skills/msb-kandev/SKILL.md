# Kandev

Detail carved out of `AGENTS.md`, which keeps only what has to hold in
every session. Repo-specific throughout; the facts here were verified on
msb 0.7.6–0.7.7. msbctl now requires 0.7.12 (`MSB_MIN`); where 0.7.12
changed something, the text says so.

`msbctl kandev <verb>` (`cmd_kandev()`, `KANDEV_VERBS`) is what the Kandev plugin runs over ssh through `host serve --kandev` (`restricted_problem(argv, kandev=True)`: kandev verbs only, and the everyday key runs none). The plugin key also runs `doctor --json`, scoped under `kandev_key()`: host checks in full, `registry_checks()` over Kandev's entries (and unparsable `k-` ones) with orphans from the Kandev label, no `github-token`/`secret-store`/`autostart`, and loose secrets files counted, never named (they are `<sandbox>.env`); `test_kandev_key_sees_no_operator_sandbox` holds that line. Every verb prints ONE JSON document on stdout (stdout is redirected to stderr meanwhile) and exits 0, or 3 with `{"error": {"code", "message"}}` where `code` is one of `KANDEV_ERROR_CODES`; raise `KandevError`, and a `die()` inside becomes `unavailable`. Off unless `[kandev] enabled` (`kandev_settings()` validates the table; `allow_extra = []` allows NO extra egress, `["*"]` anything). A Kandev sandbox is a registry entry with `source = "kandev"` (`templates/registry-kandev.toml.in`, written BEFORE `msb create` so `reap` can clean a crash up), named by `kandev_name()` (`k-<env>` or `k-<24 hex of sha256>`), looked up only by `kandev_lookup()`, which treats any non-Kandev file of that name as absent; `name_problem()` keeps `k-` from new operator names. `Sandbox` loads one (`is_kandev`, an empty `project`) so `ls`/`show`/`shell`/`exec` work; `kandev_guard()` in `main()` refuses every other operator verb, `ensure_running()` never starts one and skips all the per-boot plumbing, and `refuse_before_create()` refuses to (re)create one. Creation is `kandev_provision()`, NOT `do_create()`: no bootstrap, mounts, vsock, profile, identity, git_push, Claude token or GH_TOKEN; `--pull never` after `kandev_pull()`, labels `msbctl.owner=kandev` + `kandev.env=`, four `127.0.0.1` ports from `[kandev] port_pool` (`kandev_alloc_ports()`, under `kandev_lock()`). Secret values, registry passwords and the agentctl nonce come on stdin (`kandev_read_header()`, one JSON line, binary after it for `agentctl`) and go only into one `msb` process's environment or one `msb exec`'s stdin — tests assert they reach no argv and no file. Registry credentials: a throwaway `MSB_CONFIG_PATH` copy naming `password_env`, the value in that one pull's env (spike 16). The Kandev API is pinned by address: resolved host-side, one IP rule, and a guest `/etc/hosts` line that `kandev_pin_api()` rewrites on every start because msb regenerates the file at boot (spike 16); DNS rebind protection stays on. `kandev reap` (systemd user timer from `host kandev install`) is one pass, not a daemon; it never removes a VM lacking the label or an entry lacking the source. The proxy (`kandev_proxy()`) writes the public ports it has open to `KANDEV_PROXY_STATE` with its release; `health` reports them as `serve.ports` (feature `serve_ports`) only while a proxy of that release holds `KANDEV_PROXY_LOCK`. Both pools skip every port `registry_port_claims()` finds, of any source, running or not; `kandev_pool_overlap()` is what configure names and health counts. Data path: `tailscale serve --set-path=/vm/<name>/p/<port>` per port (`[kandev] serve`), unverified until spike 16's part 5 runs on a real tailnet node.

## Managed clients (protocol 2)

Kandev is one client; `msbctl managed <verb>` (`cmd_managed()`, `MANAGED_VERBS`) is the same verbs for any client a `[clients.NAME]` table configures, run through `host serve --client NAME` (`MSB_RESTRICTED=client:NAME`; `--kandev` stays `MSB_RESTRICTED=kandev`). Rules that must hold:

- **One parser for who.** The key's client is `key_client()` and an entry's is `entry_client()` / `entry_env()`; nothing else reads `MSB_RESTRICTED` (but `restricted()`, true for any non-empty value) or compares `source`. A scoping site that still asks `kandev_key()` or `source == "kandev"` is a cross-client leak. `kandev_key()` is defined through `key_client()`, which fails closed: a value no `host serve` sets dies, and `main()` asks it before any verb. The client comes from the forced command alone: `restricted_problem(argv, client)` refuses a `--client` in argv naming another (126), and `cmd_managed()` refuses it again (`denied`).
- **Entries.** Kandev's keep `source = "kandev"`, `kandev_env`, `msbctl.owner=kandev` + `kandev.env=`, whichever protocol made them. Other clients' are `source = "managed"`, `client`, `client_env` (`templates/registry-managed.toml.in`), labelled `msbctl.owner=<client>` + `msbctl.env=`. `Sandbox.client` / `is_managed`; `is_kandev` is an alias of `is_managed` (every site means "a client owns it: no operator plumbing"). Names are `managed_name(prefix, env)`; `name_problem()` refuses every configured prefix (`client_prefixes()`).
- **Settings.** `managed_host_settings()` (`[managed]`, else the operator's `[kandev]`, else shipped; one key in both is `invalid_config`; optional host totals from `[managed]` only), `client_settings(config, name)` (shipped `[kandev]` defaults under `[clients.NAME]`; Kandev's from `[kandev]` or `[clients.kandev]`, never both, with `KANDEV_FIXED` refusing any other prefix, ports, callback rule or `body_secret_hosts`), `clients_settings()` (never raises: every problem is its clients' own `KandevError`, a bad table name, a non-table entry, and a prefix two clients share marking each client in it, so Kandev and unaffected clients go on; under a client's key a clash names no other client; a `[clients]` that is not a table names no client but Kandev, and doctor says so). `k-` is reserved in `client_settings()` as the asking client's own error, and `default_client_prefix()` never yields it, so Kandev is never part of a clash; a broken table's prefix (`client_prefix_wanted()`) still counts in the clash check and in `client_prefixes()`. A host key (`MANAGED_HOST_KEYS`) in any `[clients.*]` table is refused. Messages about a host key name its table through `host_table()` (`[kandev]` for Kandev, as protocol 1 pins). Conflicts read the OPERATOR layer (`read_toml(CONFIG_FILE)`, or `operator=` from configure), never the merged config: defaults ship a full `[kandev]`. `kandev_settings()` returns exactly `KANDEV_SETTINGS_KEYS`, which `host kandev configure --json` prints.
- **Dialect.** `Dialect` (frozen dataclass) is the only place protocol 1 and 2 differ: `KANDEV_DIALECT` for `msbctl kandev`, `managed_dialect(settings)` for `managed` (Kandev's key included, which gets `protocols: [1, 2]` and records with `client`, while its `ls`/`show` rows stay under `kandev`, and whose guest ports stay its four: `guest_ports_settable` is false). `managed_provision` / `_agentctl` / `_start` / `_expiry` / `_lease` take it; the `kandev_*` names are thin wrappers tests patch. `body_passthrough()` gives a binding the client's `body_secret_hosts` as msb `passthrough=` (empty: none).
- **Shared host pieces.** One proxy, certificate, lease key, lock (`kandev.lock`), state dir and the `msb-kandev-*` unit names, all deliberately unrenamed (an old proxy or reaper must not race a new verb, and the plugin checks the units). `kandev_proxy_wanted()` serves every ENABLED client's entries (a broken table keeps exactly the ports it has open, never reopened from the registry, so none after a restart), and each connection must be for the listener's own client. `kandev_reap()` passes over every client, removing a VM only by its own client's label, and orphans only of configured clients. `restart-proxy` and `self-update` are Kandev-key or operator only. `tls install` is the key's of `tls_holder()` alone (and the operator's): Kandev's until exactly one other `[clients.NAME]` sets `tls = true`; two claims are each `invalid_config` and leave no holder, never falling back to Kandev; Kandev's own table may not name it.
- **KVM is the client's to ask, the operator's to allow.** A provision's optional `nested_virt` (bool) is granted only where the client's table sets `allow_nested_virt` (`denied` otherwise, never downgraded), recorded as `nested_virt` in the entry (`Sandbox.nested_virt` reads only that for a client's sandbox), and always passed as `--nested-virt=true|false`; `unsupported` before anything is written when this host has no `/dev/kvm`; `start` refuses (`denied`) a sandbox with KVM once it is revoked. `health` adds the `nested_virt` feature only where asking would be granted, so protocol 1's fixtures are unchanged on a host that does not allow it. Never read `[defaults]` or a project for a client's sandbox: they are remotely controlled.
- **Secrets.** A provision's secret may carry `headers` (`SECRET_HEADER`), stored in the entry's spec as `:headers=[...]` (`secret_bind_spec()`) so `start` keeps it. Protocol 2's `start` of a RUNNING sandbox with its secrets rotates them live (`managed_rotate()`: `VAR@HOSTS` as msb holds them, no options, one `msb modify`); protocol 1's answers it untouched. Both are `MANAGED_FEATURES`, listed in protocol 2's health only.
- **Who decides what** is a table in `docs/content/managed.md`: keep it true when a key or request field moves. Operator-held endpoints: `[clients.NAME] llms` grants `[llm.<name>]` tables; a provision's `llms` (`managed_llms()`) brings their rule, intercept port, `ca_cert`, private name and key, the key read host-side (`llm_host_values()`, `managed_llm_env()`) at provision, start and rotation, recorded as `llms`/`llm_binds` (`{{HOST_HELD}}`), never in `secret_binds`, and never sent to the client (health shows `managed_llm_doc()`). A client CA (`managed_upstream_ca()`) is for its own egress/callback host only, never an `[llm]` host, kept in `managed_ca_dir()` until `kandev_remove()`. `secret_ports()` intercepts a non-443 port only where a secret's host is allowed on it: interception is per port, for every host.
- **Protocol 1 is frozen.** `tests/test_protocol1_golden.py` pins every `kandev` verb's stdout, exit and `msb` argv, the generic verbs under the Kandev key, the `--kandev` authorized_keys line, `host kandev configure` and its file, the units and a reap pass. A change that moves a fixture is a change to what the Kandev plugin was built against: rewrite them (`MSBCTL_GOLDEN_WRITE=1`) only in a commit that says why.
